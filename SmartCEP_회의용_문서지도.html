SmartCEP Agent API 연동 협의 — 회의 사전 안내

작성: 2026-10-30 참석 대상: 넷스루 담당자·API 개발 담당자, Agent 개발 담당자 일시·방식: 상호 협의 예상 소요: 60분

1. 회의 목적

사용자가 업무 의도를 대화로 전달하면, Agent가 넷스루 API에서 템플릿과 선택값을 조회하고 시나리오 조건을 구성해 비활성 초안으로 등록하는 흐름을 협의하고자 합니다.

운영자가 포털에서 템플릿을 관리하고 콘솔에 값을 등록하면, Agent가 그 정보를 조회해 활용하는 것이 목표입니다. 사용자는 업무상 필요한 조건을 정하고, 자동으로 적용되는 조건은 확인한 뒤 등록을 승인할 수 있어야 합니다.

이번 회의에서는 정상적인 조건 구성 방법을 먼저 확인하고, 기존 API로 활용할 수 있는 정보와 추가 협의가 필요한 정보를 구분하려고 합니다. 템플릿별 업무 설명과 질문 순서는 Agent 측에서 관리할 예정이며, 신규 입력 명세 조회 API 개발을 전제로 하지 않습니다.

2. 함께 확인할 사용 흐름

  1. 사용자가 수행하려는 업무와 조건을 설명합니다.
  2. Agent가 템플릿·필드 정보와 서버에 등록된 선택값을 조회합니다.
  3. 사용자 입력과 확인된 서버 정보를 이용해 등록할 조건을 구성합니다.
  4. 저장 전 검증(dry-run)을 수행하고, 보충이 필요한 항목을 사용자에게 안내합니다.
  5. 사용자가 업무 조건과 자동 적용 내용을 확인하고 승인합니다.
  6. 비활성 상태(INACTIVE)로 저장한 뒤 재조회하여 승인 내용과 대조합니다.

여기서 dry-run은 저장하지 않고 요청 내용을 검사하는 기능입니다. 메타데이터는 필드의 타입·필수 여부·허용 연산자·선택값 등을 설명하는 정보입니다. 노드는 템플릿의 개별 구성 요소이며, 데이터소스는 그 조건이 참조하는 데이터의 구분입니다.

내부 연동 과정에는 콘솔 등록값을 Agent가 조회해 진행한 사례가 있습니다. 별도의 직접 API 시험에서는 임의값을 넣어 검증·저장을 통과한 사례도 있었으나, 해당 값은 실제 업무 조건이나 콘솔 기본값의 근거로 사용하지 않습니다. 회의에서는 콘솔에서 정상적으로 구성하는 사례를 기준으로 조회·조건 구성·검증을 비교하고자 합니다.

3. 논의 안건

안건 1. 콘솔에서 사용하는 값과 기본 조건을 Agent가 활용하는 방법

확인 배경

공식 명세는 required 시맨틱 필드를 조건에 포함하도록 안내합니다(PDF 21·45쪽). 내부 시험 보고에서는 아래 필드들이 누락 시 요구되었습니다. 각 필드의 처리 방식과 적용 범위를 함께 확인하고자 합니다.

필드내부 시험에서 요구된 데이터소스
vtime1: 화면, 2: 행동
vuid1: 화면, 2: 행동
vseq1: 화면, 2: 행동
flow1: 화면, 2: 행동
accessTime1: 화면, 2: 행동
sourceType2: 행동
sessionId2: 행동

위 번호와 요구 사항은 시험 환경에서의 관측입니다. 다른 템플릿·환경에도 같은 규칙이 적용되는지는 확인이 필요합니다.

함께 확인할 질문

  • 콘솔에서는 각 필드를 사용자가 입력하는지, 자동으로 조건을 구성하는지, 실행 시 처리하는지요?
  • Agent가 사용할 값이나 기본 조건을 기존 API의 어느 응답에서 확인할 수 있습니까?
  • 자동 조건이 있다면 값뿐 아니라 연산자와 적용 범위도 확인할 수 있습니까?
  • 조건 포함을 요구하는 기준이 템플릿·노드·데이터소스에 따라 달라집니까?
  • 현재 조회만으로 필요한 정보를 얻기 어렵다면, 기존 응답에서 기본 조건을 알려 주거나 서버가 적용 결과를 반환하는 방식 중 어느 쪽이 적절합니까?

회의에서 정할 내용: 필드별 정상 처리 방식, 조회 경로 또는 응답 보강 필요 여부, 확인용 샘플.

안건 2. 검증 결과를 정확한 보충 질문으로 연결하는 방법

확인 배경

Agent가 사용자에게 필요한 항목을 정확히 질문하려면 검증 결과가 어느 노드의 어느 필드 또는 파라미터를 가리키는지 알아야 합니다. 공식 명세에는 조건 입력이 아예 없는 노드의 오류 처리 방식이 설명되어 있습니다(PDF 32~33쪽). 개별 필드가 누락되거나 형식이 다른 경우도 함께 확인하고자 합니다.

함께 확인할 질문

  • 조건 전체 누락, 특정 필드 누락, 타입 오류, 허용값 오류, 채널 입력 누락은 각각 어떤 응답으로 구분됩니까?
  • 응답의 key만으로 정확한 입력을 식별할 수 있는 규칙이 있습니까?
  • 필요한 경우 nodeId·dataSourceId·field·parameterKey 같은 위치 정보를 추가할 수 있습니까?
  • 사용자 입력으로 해결할 항목과 운영자 확인이 필요한 항목을 어떻게 구분하면 좋습니까?
  • 독립적으로 검사 가능한 문제를 한 응답에 모아 안내할 수 있습니까? 선행 입력이 없어 검사가 어려운 경우는 어떤 정보부터 보충하면 됩니까?

회의에서 정할 내용: 대표 오류 응답과 위치 식별 방법, 한 번에 확인할 수 있는 검증 범위.

안건 3. 콘솔 선택값 조회와 변경 반영

확인 배경

Agent는 서버의 허용값 목록과 별도 값 검색 API를 이용하려고 합니다. 공식 명세의 allowedValues·metaShare·field-values를 기준으로, 선택값이 없는 경우와 별도 검색이 필요한 경우를 구분하고자 합니다(PDF 40~45쪽).

함께 확인할 질문

  • 같은 노드·데이터소스에서 조회해야 할 필드·필수 여부·허용 연산자의 범위를 어떻게 맞추면 됩니까?
  • 응답 내 선택 목록, 별도 검색, 직접 입력, 운영자 등록 필요 상태를 기존 응답에서 어떻게 구별할 수 있습니까?
  • 검색 결과 0건과 전체 선택값 미등록을 어떻게 구분합니까?
  • 콘솔에서 값을 추가·변경·삭제한 뒤 Agent가 언제 다시 조회하면 됩니까?
  • 이미 선택한 값이 승인이나 저장 전에 바뀐 경우 어떤 검증 결과를 받을 수 있습니까?

회의에서 정할 내용: 상태별 조회·안내 방식, 변경 후 재조회 기준.

안건 4. 승인한 내용의 저장과 확인, 단계별 적용

확인 배경

명세상 dry-run과 저장의 검사 범위에는 차이가 있고, 불완전한 요청이 WRITING 상태로 저장될 수 있습니다. 기간 상한은 저장 경로에서 검사되는 것으로 설명되어 있습니다(PDF 32쪽). 이 차이를 고려한 등록 절차를 맞추고자 합니다.

함께 확인할 질문

  • 기간 상한 등 저장 때 확인되는 조건을 미리 확인할 방법이 있습니까?
  • 자동 조건을 적용한다면 dry-run·저장·재조회에서 같은 내용을 확인할 수 있습니까? 중간에 설정이 바뀌면 어떻게 처리합니까?
  • 경고 발생 시 사용자 확인 후 진행할 경우와 운영자 확인이 필요한 경우를 어떻게 구분합니까?
  • 검증되지 않은 초안의 저장을 피하려면 어떤 호출 절차나 선택 기능을 사용하면 됩니까?
  • 명세의 기본 호출 제한(분당 100회)을 기준으로 실제 환경의 한도와 재시도 시 유의할 점은 무엇입니까?

회의에서 정할 내용: 저장 전 확인 사항, 변경·경고 처리, 우선 적용 범위와 검증 일정.

4. 회의 전 준비 사항

가능한 범위의 예시를 준비해 주시면 구체적으로 비교하는 데 도움이 됩니다. 사전 답변이 어려운 항목은 회의에서 확인 담당자와 후속 일정을 정해도 됩니다.

준비 주체준비할 내용
Agent 측콘솔 등록값을 조회해 진행한 대표 사례: 템플릿·노드·데이터소스 관계, 조회 조건과 응답, 구성한 등록 본문
Agent 측추가 필드가 요구된 사례와 대표 검증 응답. 실제 응답과 설명용 예시를 구분
Agent 측사용자에게 보여 줄 보충 질문·자동 적용 확인·등록 승인 흐름
넷스루 측대표 콘솔 등록 흐름에서 사용자 입력과 자동 적용 조건의 구분, 기존 API 조회 경로
넷스루 측위 7개 필드의 처리 기준과 적용 범위, 정상 조건 구성 예시
넷스루 측필드 누락·타입·허용값·경고의 대표 응답과 검증·저장의 차이
양측기준으로 사용할 공식 명세와 실제 적용 버전 확인, 공유 가능한 샘플과 후속 검증 담당

Agent 소스코드 열람 없이 요청·응답과 사용자 흐름을 기준으로 논의할 수 있도록 준비합니다. 개발망 접근이 어려우면 식별자를 치환한 샘플로 비교하며, 인증정보와 실제 고객 식별값은 제외합니다.

먼저 기존 API로 가능한 처리와 샘플을 확인하고, 응답 보강이 필요한 부분은 우선순위를 정해 단계적으로 진행하고자 합니다. 합의한 응답은 Agent 측에서 시험 환경으로 확인한 뒤 개발망에서 조회·검증·비활성 등록·재조회를 확인합니다.

작성: 2026-10-30. 대상: 넷스루 API 개발 담당자와 양측 구현·검토 도구. 상태: 협의안. 아래 추가 필드와 동작은 합의 전 제안이며 기존 서버 계약이 아니다.

1. 목적과 근거

운영자가 콘솔에 등록한 정보와 서버에서 조회한 값을 Agent가 활용해, 사용자 의도에 맞는 조건을 구성하고 비활성 초안으로 등록하는 것이 목적이다. 필요한 정보의 출처를 확인하고 보충 질문·반복 조회를 줄이는 데 초점을 둔다.

1.3 내부 결과에서 확인한 필요

  • 직접 API 시험에서는 7개 필드에 생성 문자열·상수를 넣어 dry-run 및 등록·재조회에 성공했다. 이는 전송·저장 경로 확인 자료이며, 값의 업무 적합성이나 기본값의 근거가 아니다. flow=PAGE, sourceType=PAGE를 확인된 콘솔 기본값으로 사용하지 않는다.
  • 콘솔에 등록한 값을 Agent가 조회해 진행한 사례는 정상 활용 방향이다. 조회된 값도 사용자의 의도와 해당 필드·노드·데이터소스에 맞게 선택해야 한다. 과거 등록 시나리오의 모든 조건을 새 시나리오의 기본 조건으로 복사하지 않는다.
  • 조회 집계에서 allowedValues가 없던 결과와 이후 값 목록을 확인한 분석이 함께 있다. 콘솔 설정·조회 옵션·범위·시점의 차이를 맞춰 확인한다. 어느 한쪽만으로 서버 동작의 원인을 확정하지 않는다.
  • 누락 필드를 보충한 뒤 타입 오류가 나타난 보고가 있다. 독립적으로 검사 가능한 오류를 함께 받으면 재질문을 줄일 수 있다.

2. 양측 역할과 목표 흐름

2.1 우리 쪽에서 처리하는 것

  • 포털 운영자가 만든 템플릿별 업무 의미·질문 순서는 설정과 Skill로 관리한다. 정확한 필드 매핑은 구조화 설정에 두고 템플릿 변경 시 재확인한다. 신규 input-spec API는 필수 요청이 아니다.
  • 서버 목록과 field-values에서 현재 값·라벨을 읽고 사용자 의도와 연결한다. 임의의 ID·상수나 모델 지식을 서버 값의 근거로 사용하지 않는다.
  • 메타 선언 누락만으로 준비를 막지 않고 실제 dry-run 결과를 활용한다. 오류 자유 문구는 사용자 안내에 쓰되 필드 대응의 근거로 파싱하지 않는다.
  • 준비 결과를 짧은 질문·자동 적용·운영 확인 항목으로 정리하고, 승인 본문·비활성 등록·멱등성 키·저장 후 재조회를 관리한다.
  • dev에는 같은 턴의 동일 본문·메타 범위 dry-run 재사용이 반영되어 있다. 다음 턴에는 재검사할 수 있다. 기본 준비 한도는 턴당 2회, 대화 전체 한도는 없음이며 설정 가능하다. 저장 직전 검사는 별도다.
  • 템플릿 변경 시 조건 재사용과 모든 필수 조건의 단일 선택값 자동 적용 확대는 별도 작업 브랜치에서 진행 중이다. 현재 통합 완료나 실제 개발망 검증 완료로 취급하지 않는다.

2.2 넷스루와 맞출 것

조회 가능한 정보와 정상 조건 구성 방법을 먼저 확인한다. 기존 API로 충분하면 호출 측에서 맞추고, 부족한 정보만 기존 응답에 보강하는 방안을 협의한다. 기본값 처리와 검증 동작 변경은 선택지별 영향·공수를 함께 판단한다.

목표 흐름: 템플릿·현재 메타 조회 → 업무 입력과 서버 값 연결 → dry-run → 보충 질문/확인된 기본 조건 반영 → 사용자 승인 → 저장 직전 검사 → INACTIVE 저장 → 실제 저장 내용 대조.

3. 협의 항목

REQ-API-1. 오류를 입력에 연결할 구조화 정보

목적: 사용자가 고칠 수 있는 항목을 정확히 한 번에 질문하고, 운영 조치가 필요한 항목을 구분한다.

대상: AgentValidationError와 AgentErrorDetail의 해당 오류·경고 항목. 기존 key, code, message, hint, nextAction 및 기존 추가 필드는 보존한다.

추가 항목은 해당할 때만 제공한다. 위치를 알 수 없는 노드 전체 오류에 가짜 field를 넣지 않는다. 특정 필드 누락은 가능하면 필드마다 한 항목을 제공한다. 기존 key의 형식을 바꾸는 대신 구조화 항목을 추가하는 방안을 우선한다.

먼저 확인할 샘플: 조건 전체 누락, 일부 필드 누락, 잘못된 타입, 허용값 밖 입력, 채널 파라미터 누락, 경고. 각 경우의 HTTP 상태와 응답 위치도 함께 확인한다.

REQ-API-2. 필드별 정상 조건과 기본값 처리

목적: 사용자에게 의미 없는 값을 묻거나 임의 값을 생성하지 않고 콘솔과 같은 의미의 시나리오를 구성한다.

내부 시험에서 요구된 필드는 다음과 같다. 타입·DS는 관측이며 업무 의미·기본값·처리 주체는 확인 대상이다.

vtimeNUMBER(epoch ms로 보고됨)1 화면, 2 행동콘솔 처리, 정상 조건·단위, 조건 필수 여부

accessTimeNUMBER1, 2동일. 이름만으로 단위나 뜻을 확정하지 않음

필드마다 다음을 확인한 뒤 처리 방식을 선택한다.

  1. 사용자 업무 조건이면 실제 허용 연산자·값 조회 방법을 제공하고 사용자 의도에 맞춰 구성한다.
  2. 콘솔 기본 조건이면 그 조건의 적용 범위(템플릿/노드/DS/설정 버전)를 확인한다. 단순 value뿐 아니라 필요한 config·details·subConfig·compareOperator를 포함한다.
  3. 이벤트 실행 때만 생성되고 등록 조건으로 요구할 필요가 없는 항목이면 해당 필수 검사의 적용 범위를 협의한다. 런타임 필드라는 이유만으로 업무 조건 사용 자체를 금지하지 않는다.
  4. 운영 등록이 필요한 항목이면 운영자가 먼저 등록하고 Agent가 재조회한다.

기본 조건 처리 대안:

  • 서버 선언: defaultBinding으로 완전한 기본 바인딩을 제공하고 Agent가 요청에 반영한다.
  • 서버 적용: 누락된 조건에 한해 서버가 적용하고 validation.appliedDefaults로 위치·실제 조건·근거를 반환한다.
  • 기존 조회 활용: 콘솔·템플릿 조회만으로 동일 정보를 얻을 수 있다면 그 경로와 재사용 범위를 문서화한다.

사용자가 명시한 조건은 자동 기본값으로 덮어쓰지 않는다. dry-run과 저장 사이에 기본값이나 메타가 달라질 수 있다면, 변경 감지·거절·재승인 방법을 합의한다. 조회 당시 설정과 승인한 최종 조건이 저장·재조회에서 일치해야 한다.

기본 바인딩 제안: kind=CONDITION이면 nodeId·dataSourceId·field·condition(기존 AgentCondition 전체)을, kind=PARAMETER이면 parameterKey·value를 준다. 두 종류를 섞지 않는다. condition.field는 바깥 field와 같아야 한다. basis는 템플릿/콘솔 등 근거 종류이고 sourceRef는 가능한 경우 버전이나 설정 식별자다.

기존 우리 목업·어댑터의 defaultValue 및 appliedDefaults.value는 단순 값 중심의 시범 계약이다. 완전한 조건 계약을 합의하면 우리 쪽 변환·승인 표시·재조회 비교도 함께 변경한다. 새 제안이 현재 구현에 그대로 들어간다고 가정하지 않는다.

REQ-API-3. 보충 질문을 줄이는 검증과 저장 일관성

목적: 독립적으로 검증 가능한 오류를 모아 질문하고, 저장 직전에 새로 발견되는 문제를 줄인다.

  • 조건 전체 누락 검사, 개별 조건·파라미터 검사의 실행 범위를 샘플로 확인한다. PDF 32쪽의 두 단계 설명만으로 서버 전체 검사 순서를 확정하지 않는다.
  • 파싱·식별에 필요한 정보가 있는 범위에서 누락·타입·허용값 오류를 함께 반환하는 방안을 요청한다. DS 미선택 등 후속 검사를 할 수 없는 경우는 그 선행 항목을 알린다. 불완전한 입력에 모든 검사를 무조건 실행하도록 요구하지 않는다.
  • CAP의 다중 오류 수집은 사용성 참고 사례다. CEP와 같은 구현이나 공수라고 가정하지 않는다.
  • 기간 상한 등 dry-run·저장 검증 차이를 확인하고 가능한 사전 검증 확대를 협의한다. 요청 레벨 400을 모두 200으로 바꾸는 것은 기본 요구에 포함하지 않는다.
  • 검증 실패 시 WRITING 저장을 피하는 선택이 가능한지, 어렵다면 기존 계약에서 호출 측이 무엇을 확인해야 하는지 정한다.
  • 경고별로 계속 진행/사용자 확인/운영 확인을 정한다. 우리 현재 구현은 경고에서 멈추므로 확인된 경우만 완화한다.

우선순위: 정상 조건 확인·정확한 오류 위치를 먼저, 다중 오류 수집과 저장 검증 확대를 다음 단계로 협의한다. 템플릿별 입력 안내는 우리 설정으로 보완할 수 있다.

REQ-API-4. 조회 정보와 검증의 연결 및 선택값 상태

목적: 콘솔에서 관리한 최신 값을 안전하게 사용하고, 값이 없는 경우 불필요한 질문·검색을 반복하지 않는다.

  • 동일 ruleConfigNodeId·dataSourceId·semanticType/actionType·조회 시점으로 메타와 POST를 비교한다. 등록 시 요구하는 필드가 조회 범위의 required와 어떻게 대응하는지 확인한다.
  • required 생략 규칙은 현행 명세를 적용한다. true/false 항상 명시는 편의 개선 선택지이며 필수 조건이 아니다.
  • allowedValues 생략만으로 운영 미등록을 판정하지 않는다. metaShare=true면 field-values를 사용한다. 키워드 검색 결과 0건과 전체 등록값 0건을 구분한다.
  • 아래 상태를 구별할 수 있으면 기존 필드 조합을 사용해도 된다. 부족하면 valueSource 같은 가칭 필드를 추가한다.
상태(가칭)의미Agent 행동
INLINE응답 목록이 현재 선택 도메인목록에서 선택. 전체 목록인지도 확인
LOOKUPfield-values 등 별도 조회 필요서버의 문서화된 경로로 검색·페이지 조회
DIRECT직접 입력 가능타입·연산자·형식에 맞춰 사용자 입력
UNAVAILABLE필요한 운영 등록이 없어 현재 선택 불가운영 안내 후 변경 시 재조회

UNAVAILABLE로 확인된 선택형 필드는 allowedValues=[]를 함께 제공하는 방안을 제안한다. 빈 배열만으로 모든 필드의 상태를 결정하는 계약은 만들지 않는다. 콘솔 변경 이후 캐시 무효화·재조회 기준과, 삭제된 선택값이 승인·저장 사이에 발생했을 때 처리도 합의한다.

4.2 추가 스키마 제안 (OpenAPI 3.1)

아래 이름·구조는 협의용이다. 기존 AgentCondition을 재사용한다. 기본 조건의 실제 값은 넷스루가 확인한 샘플로 채운다.

components:
  schemas:
    AgentDefaultBinding:
      oneOf:
        - $ref: '#/components/schemas/AgentConditionDefaultBinding'
        - $ref: '#/components/schemas/AgentParameterDefaultBinding'
    AgentConditionDefaultBinding:
      type: object
      required: [kind, nodeId, dataSourceId, field, condition, basis]
      properties:
        kind: {const: CONDITION}
        nodeId: {type: string}
        dataSourceId: {type: integer}
        field: {type: string}
        condition: {$ref: '#/components/schemas/AgentCondition'}
        basis: {type: string}
        sourceRef: {type: string}
      additionalProperties: false
    AgentParameterDefaultBinding:
      type: object
      required: [kind, parameterKey, value, basis]
      properties:
        kind: {const: PARAMETER}
        parameterKey: {type: string}
        value: {}
        basis: {type: string}
        sourceRef: {type: string}
      additionalProperties: false

두 오류 스키마에 추가할 properties는 아래와 같다(기존 properties와 병합). 가칭 defaultBinding은 스칼라 defaultValue와 함께 보내지 않는 것을 제안한다. 미확정 항목은 null 대신 생략한다.

nodeId: {type: string}
dataSourceId: {type: integer}
field: {type: string}
parameterKey: {type: string}
label: {type: string}
dataType: {$ref: '#/components/schemas/AgentDataType'}
expectedFormat: {type: string}
fillableBy:
  type: string
  enum: [USER, TEMPLATE_DEFAULT, ENGINE, OPERATOR]
valueSource:
  type: string
  enum: [INLINE, LOOKUP, DIRECT, UNAVAILABLE]
allowedValues:
  type: array
  items: {$ref: '#/components/schemas/FieldValueItem'}
defaultBinding: {$ref: '#/components/schemas/AgentDefaultBinding'}

AgentValidationResult.properties에 추가하는 항목:

appliedDefaults:
  type: array
  items: {$ref: '#/components/schemas/AgentDefaultBinding'}

parameter 기본값의 value 타입은 대상 파라미터 계약으로 검증한다. field 일치, 사용자 조건 우선, 적용 범위, 승인 전후 변경 검사는 JSON Schema만으로 충분하지 않으므로 서버·Agent 동작 기준으로도 검증한다.

5. 합의 후 확인 기준

ID확인 기준
AC-1조건 전체 누락·필드 일부 누락·타입·허용값·파라미터 오류를 구분하고, 알 수 있는 위치를 두 오류 스키마에서 일관되게 제공한다. message만 바뀌어도 Agent 대응이 바뀌지 않는다
AC-2콘솔 조회값·사용자 의도·확인된 기본 조건으로 구성한 시험이 dry-run valid=true를 받는다. dry-run에 WROTE나 생성 ID를 요구하지 않는다
AC-3별도 승인 후 INACTIVE 저장에서 WROTE와 생성 ID를 확인하고, GET 결과를 승인 조건·자동 적용 조건과 대조한다. 임의 생성값으로 통과시킨 사례는 업무 적합성 시험으로 세지 않는다
AC-4기본 조건은 확인된 출처·범위와 완전한 연산자 구조를 보존한다. 사용자 조건을 덮어쓰지 않고, 승인 후 변경 시 재승인/거절 등 합의 동작을 따른다
AC-5독립 검사가 가능한 오류는 함께 반환하고, 검사할 수 없는 항목은 선행 입력을 안내한다. 기간 상한 등 남은 저장 전용 검증은 명시하고 처리 시험을 한다
AC-6동일 조회 범위의 required·값·연산자가 등록 검증과 대응한다. INLINE/LOOKUP/DIRECT/UNAVAILABLE, 검색 0건/전체 0건, 콘솔 변경 후 재조회를 구별한다
AC-7기존 CEP·CAP 응답의 프로퍼티·key·HTTP 계약을 보존하거나, 변경 영향과 적용 방식을 사전에 합의한다
