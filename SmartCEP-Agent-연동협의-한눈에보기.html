사용자가 대화로 “이런 고객에게 이런 안내를 보내고 싶다”고 말하면, Agent가 넷스루 서버에서 필요한 정보를 찾아 캠페인 시나리오 초안을 꺼진 상태로 대신 만들어 준다.

01먼저 알아둘 용어

이 문서와 회의에서 반복해서 나오는 말이다.

Agent

사용자와 대화하며 API를 대신 호출해 시나리오를 만드는 AI 프로그램. 우리가 만든다.

템플릿

운영자가 포털에서 미리 만들어 둔 시나리오의 뼈대. Agent는 여기에 조건을 채운다.

예: “페이지 이탈 고객군 연동 챗봇 전송”
노드

템플릿을 이루는 개별 블록. 이벤트 감지, 대기 시간, 고객군, 발송 채널 같은 단계 하나하나다.

데이터소스 DS

조건이 참조하는 데이터의 종류. 내부 시험에서는 1번이 “화면”, 2번이 “행동” 데이터였다.

메타데이터

각 필드의 설명서. 타입, 필수 여부, 쓸 수 있는 비교 방식, 고를 수 있는 값 목록을 알려준다.

허용값 / 값 검색 allowedValues · field-values

고를 수 있는 값 목록. 값이 너무 많은 필드는 목록 대신 별도 검색 API로 찾는다.

사전 검사 dry-run

저장하지 않고 “이대로 등록하면 문제가 없는지”만 서버에 물어보는 기능.

비활성 저장 INACTIVE

시나리오를 꺼진 상태로 저장하는 것. 실제 고객에게 발송되지 않아 안전하다.

작성 중 상태 WRITING

조건이 덜 채워진 채 저장된 상태. 의도치 않게 이렇게 저장되는 것을 피하고 싶다.

03역할 분담 — 우리가 할 일과 넷스루와 맞출 일

새 API를 만들어 달라는 회의가 아니다. 기존 API로 되는 것은 우리가 맞추고, 정말 부족한 정보만 기존 응답에 보강하는 방향이다.

우리 쪽 · Agent
  • 템플릿별 업무 의미와 질문 순서는 우리 설정과 Skill로 관리한다. 신규 입력 명세 API는 요청하지 않는다.
  • 값은 반드시 서버 목록과 값 검색에서 읽는다. 임의의 ID나 AI가 짐작한 값을 쓰지 않는다.
  • 사전 검사 결과를 짧은 질문, 자동 적용, 운영 확인 항목으로 나눠 보여준다.
  • 승인된 본문으로 꺼진 상태 저장, 중복 방지 키, 저장 후 재조회를 관리한다.
  • 같은 턴에 같은 본문을 다시 검사하지 않는다. 기본 준비 검사는 턴당 2회로 제한한다.
넷스루와 맞출 것
  • 콘솔에서 정상적으로 조건을 구성하는 방법과, 그 정보를 기존 API 어디서 읽을 수 있는지.
  • 사전 검사 오류가 정확히 어느 노드·필드를 가리키는지 알려주는 방법.
  • 선택값이 “목록에 있음 / 검색 필요 / 직접 입력 / 아직 등록 안 됨” 중 무엇인지 구별하는 방법.
  • 사전 검사와 실제 저장의 검사 차이, 경고 처리, 자동 조건의 일관성.
  • 기본값 처리와 검증 동작을 바꾼다면 선택지별 영향과 공수.

  2. 위 4가지 상태를 기존 응답에서 어떻게 구별할 수 있나요?

  5. 이미 고른 값이 승인이나 저장 전에 바뀌면 어떤 검증 결과를 받나요?

승인한 내용의 저장과 확인, 단계별 적용

사전 검사를 통과했는데 저장에서 새 문제가 나오거나, 덜 채운 초안이 저장되는 일을 줄이기 위한 안건이다.

검사 범위의 차이
사전 검사 dry-run
조건 전체 누락필드 누락타입허용값그 외 범위는 샘플로 확인
실제 저장
조건 전체 누락필드 누락타입허용값기간 상한 (저장 때만)
위험사전 검사를 통과해도 저장에서 기간 상한에 걸릴 수 있다. 또 불완전한 요청이 작성 중(WRITING) 상태로 저장될 수 있다. 저장 전 확인을 넓히거나, 검증 실패 시 저장을 피하는 방법을 정해야 한다.
한 번에 모아 받기

내부 시험에서 빠진 필드를 채우고 나니 그제서야 타입 오류가 나온 사례가 있었다. 함께 검사할 수 있는 오류는 한 번에 받으면 사용자에게 묻는 횟수가 줄어든다.

지금 · 하나씩
누락 오류→질문 1→타입 오류→질문 2→통과
제안 · 모아서
누락 + 타입 + 허용값→질문 1회→통과

데이터소스를 고르지 않아 뒤 검사를 할 수 없는 경우까지 모두 검사하라는 요구는 아니다. 그럴 때는 무엇부터 채워야 하는지 알려주면 된다. CAP 쪽의 다중 오류 수집은 참고 사례일 뿐 같은 공수라고 보지 않는다.

경고는 어떻게
계속 진행사용자 확인 후 진행운영자 확인 필요

경고마다 셋 중 무엇인지 정한다. 지금 우리 구현은 경고가 나오면 멈추므로, 확인된 경고만 완화한다.

  3. 경고 중 사용자 확인으로 넘어가도 되는 것과 운영자 확인이 필요한 것은 어떻게 구분하나요?
  4. 검증되지 않은 초안이 저장되지 않게 하려면 어떤 절차나 옵션을 쓰면 되나요?

07근거의 무게 — 어디까지 믿을 수 있나

이 협의는 출처가 다른 자료를 섞어 쓴다. 각 자료를 어디까지 근거로 쓰는지 정해 두었다.

구분자료어디까지 쓰나
공식 계약OpenAPI YAML 1.0.0, 넷스루 명세 PDF(2026-07)엔드포인트·스키마·명세상 동작. 실제 배포와의 차이는 샘플 응답으로 확인

우리 구현dev 브랜치 기준 호출 측 개선우리가 고친 부분. 개발망에 같은 버전이 배포됐다는 뜻은 아님

제안REQ-API-1~4와 추가 스키마수용 범위·이름·적용 방식은 회의 후 확정

공식 명세로 이미 알 수 있는 것 — 다시 요청하지 않는다

  • 필수 필드 목록이 비어 있을 수 있다. 데이터소스가 여럿인 노드는 원래 비워서 준다. 비어 있다고 템플릿 오류로 보지 않는다. PDF 21쪽
  • 불완전한 저장은 작성 중 상태가 될 수 있고, 기간 상한은 저장 때만 본다. PDF 32쪽
  • 오류 코드 목록은 이미 있다. 필드 위치·경고·행동 코드처럼 확인되지 않은 부분만 보충한다. PDF 34~35쪽
  • 값 목록이 없다고 미등록은 아니다. 값이 많은 필드는 별도 검색을 쓴다. PDF 42~45쪽
  • 기본 호출 한도는 분당 100회다. 환경별 설정과 재시도 정책은 확인한다. PDF 11쪽
